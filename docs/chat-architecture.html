/tab/chat AI 对话功能技术架构

这是一个「浏览器负责会话编排与本地文件计算，Next.js 服务端负责密钥隔离与模型网关」的混合架构。 核心调度器是 useChat()，一次发送会按优先级被分配到四套执行引擎之一。

入口与编排 Client Component + useChat 页面只组合 UI；消息、路由、SSE 流、附件、记忆与取消全部由 Hook 协调。
执行引擎 4 条主链路 普通 SSE · Pi Agent 工具循环 · CSV 本地分析循环 · 长期记忆闭环。
数据边界 原始文件留在浏览器 模型只接收提示词、文件描述、样例与有界查询结果；API 密钥只在服务端。
持久化 无数据库 会话在 sessionStorage，长期记忆在 localStorage，原始文件仅在 Worker 内存。
一句话运行原理

用户发送后 handleSend() 先组装引用、长期记忆与 Agent 提示词，再按 「Thinking / 联网 / 文件附件 / CSV」条件选择引擎；执行过程把 reasoning/content 增量写回当前会话， 成功后异步排队更新长期记忆，失败或停止时按链路语义降级。

关键数字

会话上限 20 Pi Agent 12 回合 / 24 工具 / 5 搜索 CSV ≤ 50MB，查询循环 ≤ 12 轮，每轮 ≤ 8 个查询 普通消息压缩至最近 12 条 Pi 历史 ≤ 24 条（每条 120k 字符） 记忆 Prompt ≤ 2,000 字符，来源 ≤ 16 条 记忆保留 180 天，每用户 ≤ 100 条 /api/chat 限时 180s，工具协商 ≤ 5 轮 QuickJS 沙箱 32MB / 1.5s

一次发送的分流

分流逻辑在 src/hooks/use-chat.ts 的 handleSend()，严格按优先级提前返回。

① 前置校验空内容且无附件 · 无会话 · 该会话已有请求 · 附件尚未就绪 → 直接返回
② 引用消息拼接quotedMessages 以 blockquote 前缀并入用户消息
③ 附件分类与任务路由csv-analysis（CSV 本地分析件）· file（通用文件）· classifyPiTask 正则判断「联网意向 / 文件上下文引用」
④ 记忆检索selectMemoryContext → 当前会话摘要 + 相关历史（≤3）+ 稳定偏好（≤6）→ memoryPrompt（≤2000 字符）
⑤ 引擎选择（第一个命中）条件见下方四张卡片，命中后写入用户消息 + 占位助手消息并立即返回

Pi Agent 工具循环 P1

enableThinking || requestsWebSearch || genericFileAttachments > 0 || shouldUseFileContexts

handlePiThinkingSend() → 浏览器端 Agent 多回合运行，模型经 /api/stream 代理。

开启 Thinking、明确要求联网、或携带通用文件附件时，整条消息切换为引擎 1 —— thinking 是架构开关而非参数。

新 CSV 本地分析 P2

csvAnalysisAttachments.length > 0

handleCsvAnalysisSend() → 对每个新上传 CSV 执行「模型规划查询 → Worker 本地执行」循环，多文件最后综合。

仅当未命中 P1 时进入；发送前要求字段画像已就绪（profiled）。

CSV 上下文追问 P3

activeCsvContexts.length > 0

handleCsvContextFollowup() → 复用页面生命周期内保存的 CSV Worker 与已有查询结果，继续有界查询。

上下文存于 csvContextsRef（按 sessionId 分桶），刷新页面后不可恢复。

otherwise

POST /api/chat → 无工具时直接流式；Agent 配置 enableSearch 时由服务端执行工具协商。

最短路径：客户端消费归一化的 reasoning / content / done 事件。

容易误解的「双搜索入口」： 用户显式说「联网 / 搜索新闻」会被正则送入 P1（浏览器端 web_search 工具 + Tavily 代理）； 而选择「市场分析 / 营销策划」等 Agent 且未提联网词时走 P4，由服务端 enableSearch 驱动 search_web tool-calling。两条链路调用同一个 Tavily 搜索，但协商位置不同。

状态与存储矩阵

判断「刷新后还在不在」比理解组件树更关键：状态分散在四类存储中。

数据位置生命周期关键行为
会话、消息、Agent、草稿、引用、语言、Thinking chat-store / sessionStorage 同标签页会话 手动 rehydrate；≤20 会话；第一条用户消息自动成为标题；每条消息保留 attachments 中的文件摘要。
长期记忆 chat-memory-store / localStorage 跨刷新与重开 按 Teams 用户或 browser owner 隔离；100 条 / 180 天；用于发送前的记忆 Prompt。
Dev 提示词覆盖 prompt-override-store / localStorage 长期本地 覆盖全局规则或单个 Agent 专属提示词，DevPanel 中可编辑。
待发送附件（已注册文件） useSessionAttachments React state 页面内存 按 session 分桶；切换会话保留，页面卸载即丢。
原始通用文件（File 对象） 每文件一个 File Worker 页面生命周期 发送后仅持久化 descriptor（含 ≤2000 字符样例）；刷新后追问需重新上传。
CSV 全量 rows 与画像 每 CSV 一个 Worker 页面生命周期 Worker 内执行有界查询；持久化消息不含原始 rows。
活动 CSV / 文件上下文 csvContextsRef / fileContextsRef 页面内存 用于追问；删除会话或卸载时释放对应 Worker。
进行中请求 + AbortController SessionRequestRegistry 请求期间 每会话同时只允许 1 个请求；不同会话可并发生成；停止只影响当前会话。

关键设计与风险

这些行为最容易在排查问题或扩展能力时被忽略。

Thinking 是架构开关

它不只是给同一请求加推理参数：开启后普通消息也会改走浏览器端 Pi Agent，多一次配置请求，并进入多回合工具运行时。

多会话请求可并行

请求注册表以 sessionId 为键。切换会话不会中止旧请求，旧请求仍写回自己的会话；停止按钮只影响当前活动会话。

隐私边界是「原文不整体上传」

文件描述含 ≤2000 字符样例，工具返回的片段/聚合结果也会发给模型。准确表述：原始完整文件留在浏览器，模型只看到有界样本。

CSV 多文件逐个、串行分析

上传画像可并行（Promise.all），但发送后的 for...of 查询分析串行；所有单文件完成后才进入 combine 交叉综合。

DSML 工具调用兼容

/api/chat 会解析 DeepSeek 偶发输出在 content 中的 〈invoke〉DSML 标记，手动转为 tool_calls，避免搜索协商失效。

刷新会切断文件追问能力

消息与文件摘要还在，但 Worker 与 refs 已丢失。通用文件路径会提示重新上传；CSV 活动上下文同样无法从持久化消息重建。

停止生成并非端到端取消

/api/stream 将 request.signal 传给 DeepSeek；而 /api/chat 与 CSV 分析端点的上游 fetch 未统一绑定客户端 signal，客户端停止后上游可能继续消耗。

流式更新频繁持久化

每个 reasoning/content 增量都触发 updateSessionMessages；因 store 启用 persist，中长回答会产生密集的 sessionStorage 序列化。

useChat 是主要复杂度集中点

UI 已组件化，但 ~2,300 行 Hook 同时负责路由、SSE、Agent、附件、CSV 与记忆。新增第四种执行器前应优先抽离统一 request lifecycle。

双搜索路径维护成本

P1 的 web_search（Tavily 代理 + 预算）与 P4 的 search_web（服务端协商 + 退避）职责重叠，改造搜索时需同时更新两处。

本文档描述当前工作区源码的实际调用关系（依据 src/ 静态分析），不代表外部服务 SLA。纯静态 HTML、零外部依赖，可直接用浏览器打开或通过 `python3 -m http.server` 预览。
