/tab/chat AI 对话模块

这是一个“浏览器负责会话编排与本地工具，Next.js 负责密钥隔离与模型代理”的混合架构。核心调度器是 useChat()，它会把一次发送分配给三套不同的执行引擎。

入口与编排 Client Component + useChat 页面只组合 UI；消息、路由、流、附件、记忆和取消由 Hook 统一协调。
执行引擎 3 条主链路 普通 SSE、Pi Agent 工具循环、CSV 本地查询循环。
数据边界 原始文件留在浏览器 模型只接收提示词、文件描述、样例和有界查询结果；API 密钥只在服务端。
一句话运行原理

用户发送后，handleSend() 先组合引用、长期记忆和 Agent 提示词，再根据 thinking、联网意图和文件上下文选择执行器；执行过程持续把 reasoning/content 写回当前会话，成功后异步更新长期记忆。

系统边界

浏览器既是 UI，也是 Agent 编排器和文件计算节点；Next.js Route Handler 是 BFF 与模型网关。

thinking、显式联网或通用文件会切换整套运行架构。

enableThinking || requestsWebSearch || genericFileAttached || activeGenericFileContext
调用 handlePiThinkingSend()，模型经 /api/stream 多回合运行。

新 CSV 本地分析

仅在未命中 Pi Agent 时处理新上传的大 CSV。

csvAnalysisAttachments.length > 0
调用 handleCsvAnalysisSend()，执行“模型规划 - 本地查询”循环。

CSV 上下文追问

复用当前页面生命周期内保留的 CSV Worker 与阶段结果。

activeCsvContexts.length > 0
调用 handleCsvContextFollowup()，继续有界查询并重写上下文。

普通对话 SSE

无特殊能力要求时走最短路径。

otherwise
调用 POST /api/chat，客户端消费 reasoning/content/done 事件。
容易误解的“双搜索入口”： 用户明确说“联网/搜索新闻”等词时，正则会把请求送入 Pi Agent；但选择“市场分析/营销策划”且没有显式联网词时，请求仍可能走普通 /api/chat，再由 Agent 的 enableSearch 触发服务端 tool-calling。

运行时序

四个视图分别展示普通生成、Agent 工具回路、CSV 本地分析与记忆闭环。

Chat UI-> useChat-> /api/chat-> DeepSeek-> SSE -> Zustand
#执行者动作产物
1useChat创建 user message 和空 assistant placeholder，立即写入会话。updatedMessages
2useChat构造 system prompt；必要时将历史压缩到最近 12 条，再把附件摘要拼入用户消息。messages[]
3/api/chat无搜索时直接请求 DeepSeek 流；启用搜索时先执行最多 5 轮非流式工具协商。DeepSeek response
4/api/chat将供应商 SSE 归一化为 reasoning / content / done；已在工具协商阶段生成的完整答复会包装成静态 SSE。text/event-stream
5useChat按行解析 data:，累加 reasoning 与 content，每个增量更新同一个 assistant message。Zustand update
6Memory非错误答案完成后，后台排队生成会话摘要；主回复不等待记忆写入。scheduleMemoryUpdate()
Browser Agent-> /api/stream-> DeepSeek-> Tool execution-> Next turn
#执行者动作产物
1runPiAgent读取服务端预算，创建浏览器端 Agent；系统提示词追加工具规则与文件目录。Agent state
2streamProxy每个模型回合把 context 发送到 /api/stream；服务端持有密钥并调用 DeepSeek。proxy SSE events
3Browser Agent接收 thinking/text/tool-call 事件。thinking/text 实时回写消息；tool call 交给客户端工具。AgentEvent
4Client tools可调用 Web Search、CSV 查询、通用文件 inspect/search/read/query，或 QuickJS 分析脚本。bounded JSON/text
5Browser Agent把工具结果加入上下文，继续下一模型回合，直到无工具结果、达到预算或被取消。finalContent
6Budget默认限制为 12 个模型回合、24 次工具、5 次搜索，可由服务端环境变量覆盖。budget snapshot
CSV Worker profile-> /analysis/query-> Worker query-> query / combine-> Final answer
#执行者动作产物
1CSV Worker上传即在浏览器解析最多 50 MB 的 CSV，保存全部 rows，生成字段类型、语义、样例和数据质量画像。CsvProfile + rows
2/analysis/query只接收压缩画像、问题、已有结果和阶段摘要；模型返回最多 8 个有界查询或直接返回 finalAnswer。DataQueryDecision
3CSV Worker本地执行 rows/columns/filter/distinct/stats/aggregate，原始 CSV 不上传。CsvDataQueryResult[]
4useChat为每轮结果生成阶段性结论，去除重复查询，并再次请求模型；最多 12 轮。stageSummaries[]
5Fallback规划失败时生成本地后备聚合；总结失败时基于已查询结果生成本地保底摘要。recoverable result
6/analysis/combine多文件逐个分析后，将各文件压缩结论交给模型做交叉综合。combined summary
Retrieve-> Inject prompt-> Generate answer-> Summarize-> localStorage

1Retrieval发送前选择当前会话摘要、最多 3 条相关历史和最多 6 条稳定偏好。MemorySelection
2Scoring相关性基于标签/词项包含关系，再叠加时效、相同 Agent 和 confidence；不是向量检索。score
3Prompt记忆以“不可信参考信息”追加到 system prompt，最多 2,000 字符；存在当前摘要时历史消息压到最近 12 条。memoryPrompt
4Queue成功回复后按 owner + session 串行排队，仅总结尚未处理的最近消息。sourceMessages

提示词与上下文组装

同一 UI 下的三套执行引擎并不共享完全相同的上下文协议。

effectiveSystemPrompt =
  (promptOverride.globalRules || GLOBAL_EMPHASIS)
  + (promptOverride.agentPrompts[agentId] || agentSpecificPrompt)

fullSystemPrompt =
  effectiveSystemPrompt
  + selectedMemoryPrompt
  + languageInstruction

普通 /api/chat

  • 第 1 条消息是完整 system prompt。
  • 无当前记忆时可发送完整会话；有当前记忆时只取最近 12 条。
  • 用户消息中的附件 content 会被直接拼接。
  • Agent 的 enableSearch 决定服务端是否开放 search_web。

Pi Agent

  • 在完整 system prompt 后追加 Agent 循环规则与工具预算。
  • 追加通用文件目录和旧版 CSV 目录。
  • 历史最多 24 条，单条和总 prompt 都有字符上限。
  • 工具结果进入后续模型回合，而非一次性拼入首个请求。

专用 CSV Planner

  • 使用独立的 CSV 查询系统提示词。
  • 选中 Agent 只映射为 campaign/general 领域，不直接复用 Agent 专属 prompt。
  • 模型只看压缩画像、阶段摘要和有界查询结果。
  • force_final 阶段只能返回最终答案。

状态与生命周期

理解“刷新后还在不在”比理解组件树更关键：不同状态分散在三类存储中。

数据位置生命周期关键行为
会话、消息、Agent、草稿、引用、语言、thinking chat-store / sessionStorage 同一标签页会话 手动 rehydrate；最多 20 个会话；第一条用户消息自动成为标题。
长期记忆 chat-memory-store / localStorage 跨刷新与重开 按 Teams 用户或 browser owner 隔离；100 条/180 天。
开发者提示词覆盖 prompt-override-store / localStorage 长期本地 覆盖全局规则或单个 Agent 专属提示词。
待发送附件 useSessionAttachments React state/ref 页面内存 按 session 分桶；可在切换会话时保留，但页面卸载即丢失。
原始通用文件 每文件一个 File Worker 当前页面生命周期 发送后只持久化描述信息；刷新后继续追问需要重新上传。
CSV 全量 rows 与字段画像 每 CSV 一个 Worker 当前页面生命周期 Worker 内执行有界查询；持久化消息不包含原始 rows。
活动 CSV / 通用文件上下文 csvContextsRef / fileContextsRef 页面内存 用于后续追问；删除会话或页面卸载时释放 Worker。
请求与 AbortController SessionRequestRegistry 请求期间 每个会话最多一个请求；不同会话可以并发生成。

关键观察与维护边界

这些行为最容易在排查问题或扩展能力时被忽略。

thinking 是架构开关

它不只是给同一请求增加推理参数。开启后普通消息也会改走浏览器端 Pi Agent，多一次配置读取，并进入多回合工具运行时。

多会话请求可以并行

请求注册表以 sessionId 为键。切换会话不会中止旧请求，旧请求仍写回自己的会话；停止按钮只停止当前活动会话。

文件隐私是“原文不整体上传”

通用文件描述里含最多约 2,000 字符样例，工具返回的片段/聚合也会发给模型。准确表述应是“原始完整文件留在浏览器”。

多 CSV 当前逐个分析

上传画像使用 Promise.all，但发送后的 for...of 查询分析是串行；所有单文件完成后才调用 combine。

刷新会切断文件追问能力

消息和文件描述可能还在，但 Worker 与 refs 已丢失。通用文件路径会提示重新上传；CSV 活动上下文同样无法从持久化消息重建。

停止生成并非所有链路都端到端取消

/api/stream 把 request.signal 传给 DeepSeek；普通 /api/chat 与 CSV 分析端点的上游 fetch 当前没有统一绑定该 signal，客户端停止后上游仍可能继续。

流式更新会频繁持久化

每个 content/reasoning 增量都会调用 Zustand 的 updateSessionMessages；由于 store 使用 persist，中长回答会产生密集的 sessionStorage 序列化。

useChat 是主要复杂度集中点

UI 已拆成组件，但约 2,300 行 Hook 同时负责路由、SSE、Agent、附件、CSV 和记忆接入。新增第四种执行器时应优先抽离统一的 request lifecycle。

当前活跃调用链之外： /api/chat/analysis/plan、/api/chat/analysis/summarize 和 executePlanInWorker() 仍保留在仓库，但当前 useChat 已改用 /analysis/query + /analysis/combine 的自由查询流程。
